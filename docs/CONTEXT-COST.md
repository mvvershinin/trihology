# Расход контекста: замер, пороги, два предохранителя

Замер 14.09.2026. Документ объясняет, почему в проекте стоят два сторожа
(`.claude/hooks/`), откуда взяты их пороги и как перемерить всё заново.

Сюда ведут оба хука, когда отказывают человеку или показывают предупреждение.

> **Этот документ сам крупнее порога** (около 30 000 байт против 20 000), поэтому
> `cat docs/CONTEXT-COST.md` получит отказ от сторожа. Так и задумано: читать
> разделами — `grep -n '^##' docs/CONTEXT-COST.md`, потом нужный кусок через
> `sed -n 'A,Bp'`. Если нужен целиком — `cat docs/CONTEXT-COST.md | head -n 100000`.

---

## Главное в трёх строках

1. Контекст перечитывается **каждым следующим запросом сессии**. Лишний дамп
   файла оплачивается не один раз, а столько раз, сколько запросов осталось.
2. Поэтому дорого не «прочитать большой файл», а «прочитать его рано».
3. Два сторожа: один не даёт вывалить файл целиком, второй говорит вслух,
   когда сессия пора закрывать.

## Замер 4. Проверка чисел соседнего проекта

Числа `trade` перемерены своим скриптом по его 8 транскриптам, а не взяты на
слово. Два из трёх сошлись, третье — нет:

| Утверждение | Заявлено | Померено | Итог |
|---|---:|---:|---|
| Чтение кэша в весе проекта | 70 % | **70 %** | сошлось |
| Три длиннейшие сессии в чтении кэша | 64 % | **63 %** | сошлось |
| Доля `Bash` в выдаче инструментов | 58 % | **78 %** | разные знаменатели |

Попутно сошлись и контрольные величины: 7 249 запросов против заявленных 7 006,
вес 439 млн против 431 млн (замер сделан позже, поэтому чуть больше).

**Про расхождение по `Bash`.** Считать можно двумя способами, и они дают разное:

- **что реально увидела модель** — блоки `tool_result` внутри `message.content`.
  Всего 3,16 млн символов (~791 тыс. токенов), доля `Bash` — **78 %**;
- **полная запись на диске** — отдельное поле `toolUseResult`. Всего 26,6 млн
  символов, но привязать их к инструменту не удалось: `sourceToolAssistantUUID`
  не совпадает с идентификаторами вызовов.

Для расхода контекста верен первый способ: в контекст попадает ровно то, что
лежит в `message.content`. Крупная выдача `Bash` при этом ещё и сохраняется в
файл (`persistedOutputPath`), а модель видит урезанную — то есть 78 % получены
уже после урезания.

Проверка сходимости пройдена: 791 тыс. токенов выдачи инструментов укладывается
в 3,09 млрд токенов фактического чтения кэша.

**Расхождение разъяснилось.** Оба числа верны, знаменатели разные: 58 % — доля
`Bash` в сумме «вход инструмента плюс выдача» (4,26 млн из 7,30 млн символов),
78 % — доля в одной только выдаче. Для расхода контекста важна выдача, поэтому
в комментариях хуков стоит 78 % — с пометкой, что это чужой проект.

Вывод не меняется ни при 58 %, ни при 78 %: `Bash` — главный источник, и сторож
стоит на нём правильно.

## Замер 5. Оба сторожа проверены на живом пути

Не подачей JSON на скрипт, а настоящим вызовом из сессии.

`cat docs/AGENTS_PLAN.md` (21 955 байт) → отказ пришёл, файл в контекст не попал.

При проверке нашлись **четыре дефекта**, все исправлены и перепроверены.

Два первых — одного рода: **посторонняя часть команды выключала проверку
у всей команды целиком**. Это главный урок разбора, и он важнее обоих
частных случаев.

✅ **Дефект 1 — перенаправление stderr отключало сторожа целиком**
✅ Гейт `case "$CMD" in *'>'*) exit 0` считал записью файла любое `>`, включая
   `2>/dev/null` и `2>&1`. А это обычный хвост почти любой команды: из первых
   четырёх команд этой сессии три несли такой хвост. `cat большой_файл 2>/dev/null`
   проходил насквозь — сторож был выключен ровно тем, как обычно пишутся команды
✅ Исправление: хвосты stderr снимаются со строки **до** разбора. Перенаправление
   stdout (`> файл`, `&> файл`) по-прежнему пропускается — там выдача
   действительно уходит мимо контекста

✅ **Дефект 2 — один `>` или heredoc где угодно снимал проверку со всех чтений**
✅ Тот же гейт работал по всей строке, а разбор ниже — по звеньям. Поэтому
   `cat большой_файл; echo done > /tmp/x` и `cat большой_файл && python3 - <<PY`
   проходили насквозь: запись в конце команды отменяла проверку чтения в начале
✅ Особенно опасно из-за heredoc: это основной способ писать файлы в такой
   работе, то есть сторож молчал бы в заметной части команд
✅ Исправление: гейта по всей строке больше нет. Команда разбирается на
   утверждения (`;`, `&&`, `||`), внутри — на звенья конвейера. Запись
   отключает проверку только у своего утверждения; ограничитель в любом звене
   конвейера сужает весь конвейер
✅ Тела heredoc вырезаются до разбора — иначе документ, внутри которого написано
   `cat крупный_файл`, читался бы как команда чтения. Проверено: запись такого
   документа проходит, а настоящее чтение рядом с heredoc блокируется

✅ **Дефект 3 — ветка без `jq` была нерабочей**
✅ Четыре строки скопированы из другого места скрипта и обращались к `RAZBOR`
   до того, как он появится; при `set -u` это обрывает хук. Плюс `read -r CMD SID`
   рвал команду по первому пробелу
✅ Исправление: разбор через два поля на отдельных строках. Проверено запуском
   с подменённым `command -v jq`
✅ Это ровно тот отказ, о котором предупреждает шапка самого хука: сторож,
   который при своей поломке молча пропускает всё, хуже отсутствующего. На этой
   машине `jq` есть, так что ветка была спящей — но она включилась бы на машине
   без `jq`, то есть при переносе

✅ **Дефект 4 — цикл по файлам рвал имена с пробелами**
✅ Попутно: первая правка увела цикл в подоболочку через конвейер, где `exit 2`
   закрыл бы только её. Заменено на here-string

Матрица после исправления — 24 случая, все ведут себя верно:

| Блокируется | Проходит |
|---|---|
| `cat docs/AGENTS_PLAN.md` | `cat … \| head -n 50` |
| `cat docs/AGENTS_PLAN.md 2>/dev/null` | `sed -n '1,50p' docs/AGENTS_PLAN.md` |
| `cat docs/AGENTS_PLAN.md 2>&1` | `cat docs/ARCHITECTURE.md` (18 099 < порога) |
| `cat docs/METHODOLOGY.md 2> /dev/null` | `grep -n TODO docs/METHODOLOGY.md` |
| `cat $F` (имя в переменной) | `wc -l docs/METHODOLOGY.md` |
| `cat $F 2>/dev/null` | `cat … \| head -n 100000` (явный выход) |
| `sed -n '1,2000p' …` (шире 500 строк) | `cat … > /tmp/copy.md` (запись) |
| `cat большой; echo done > /tmp/x` | `cat > /tmp/x <<EOF` (запись) |
| `cat большой && echo ok > /tmp/y` | `ls -la 2>&1 \| head -30` |
| `echo start > /tmp/z && cat большой` | `git status --short` |
| `cat большой && python3 - <<PY` | `python3 - <<PY` (скрипт без чтения) |
| `cat /абсолютный/путь/большой` | запись документа, в теле которого `cat большой` |

`cd /чужой/каталог && cat большой` в этой таблице нет намеренно: он **проходит**,
и это известное ограничение, разобранное ниже в «Чего в сторожах намеренно нет».

Проверено и на живом пути (настоящим вызовом из сессии, а не подачей JSON на
скрипт), и в обеих запасных ветках — без `jq` и без `python3`.

## Замер 6. Сколько это на самом деле экономит

Считалось не прикидкой: сторож прогнан по **реальной истории команд** соседнего
проекта — 2 414 вызовов `Bash` за 8 сессий.

### ⚠️ Сначала то, что переворачивает исходную посылку

**Claude Code сам режет выдачу `Bash` примерно на 18 000 символах.** Всё, что
длиннее, заменяется заглушкой, а полный текст уходит в файл:

```
<persisted-output> Output too large (215.7KB). Full output saved to: …
```

Померено: из 2 415 выдач `Bash` **ни одна не превысила 20 000 символов**.
Максимум — 18 129. Персентили: p50 = 437, p90 = 2 348, p99 = 10 114.
Десять выдач урезаны, на диске они занимают от 40 КБ до 565 КБ.

Значит `cat` файла на 829 КБ **не кладёт в контекст 207 тысяч токенов**. Он
кладёт обрывок на пару тысяч — и не даёт содержимого, ради которого затевался.

Из-за этого в отказе хука раньше стояла неправда («примерно $((SZ/4)) токенов»).
Исправлено: теперь хук говорит то, что есть, — файл целиком не придёт всё равно.

### Сторож выдачи: около 1 %

Прогон по фактическому потоку `trade`:

| Величина | Значение |
|---|---|
| Вызовов `Bash` | 2 414 |
| Из них незащищённых чтений файла | 151 |
| Из них поймал бы сторож (выдача у потолка урезания) | **14** |
| Прямая экономия | 46 305 токенов |
| С перечитыванием до конца сессий | 35,3 млн токенов чтения кэша |
| **Доля от всего чтения контекста (3,17 млрд)** | **1,1 %** |
| Доля от общего веса проекта | ≈ 0,8 % |

То есть блокировка дампов — **проценты, а не разы**. Это не довод её снимать:
цена сторожа тоже близка к нулю, а привычку читать прицельно он ставит. Но
считать его главным приёмом нельзя.

### Сторож длины сессии: до 70 %, но платит человек

Моделирование на фактических кривых восьми сессий `trade`. Правило: как только
контекст переваливает порог — `/clear`, новая сессия стартует с исходного
контекста плюс 3 000 токенов на файл состояния.

| Порог | Срез чтения контекста | Перезапусков за 8 сессий |
|---:|---:|---:|
| 150k | 83 % | 51 |
| 200k | 79 % | 34 |
| **300k** | **70 %** | **18** |
| 400k | 62 % | 13 |
| 500k | 54 % | 9 |

При пороге 300k: 3,17 млрд токенов чтения превращаются в 945 млн. В пересчёте
на общий вес проекта это примерно **половина всего расхода**.

Здесь и лежат деньги — не в дампах файлов, а в длине сессий. Но хук ничего не
режет сам: он показывает строку, а `/clear` делает человек. Экономия равна
доле случаев, когда человек его послушал.

Оценка оптимистична: модель считает, что после `/clear` работа идёт так же.
На деле часть контекста придётся восстанавливать, и что-то будет переделано.

### А что это даёт нам

Скорее всего — **почти ничего, пока сессии короткие.**

Единственная наша сессия дала пик 81 тысячу токенов на 42 запросах (138 тысяч
на одном запросе с разбором). До порога 300k она не дошла и близко, значит
второй сторож у нас не сработал бы ни разу. А первый ловит проценты.

Оба поставлены не ради сегодняшней экономии, а на вырост: проект уже дорос до
дерева в 319 тысяч токенов, и первая же долгая сессия по сборке или отладке
приведёт к тем самым кривым. Тогда порог 300k начнёт окупаться.

**Вывод в одну строку.** Резать дампы — 1 %. Не засиживаться в одной сессии —
до половины расхода. Второе важнее первого в пятьдесят раз.

## Как выйти из-под сторожа, когда файл правда нужен целиком

Это не обход, а предусмотренный выход. Сторож требует не «не читай», а
«назови потолок выдачи»:

```bash
cat файл | head -n 100000        # явно: нужен целиком, беру ответственность
sed -n '120,180p' файл           # узкий диапазон (до 500 строк) проходит
grep -n 'def analyze' файл       # по признаку
wc -l файл                       # нужен объём, а не содержимое
```

Отдельный случай — **имя файла в переменной** (`cat $F`). Хук видит команду до
подстановки переменных и развернуть её не может: это было бы исполнением
команды. Поэтому он не спрашивает «какой это файл», а требует ограничитель —
тогда потолок выдачи известен независимо от того, что за файл.

## Второй сторож: длина сессии

`context-budget-guard.sh` (на событие `Stop`) ничего не блокирует. После
300 000 токенов он показывает строку с текущим размером контекста и напоминает
про `docs/HANDOFF.md`. Не пилит: следующая строка — только когда выросло ещё
на 100 000.

**Зачем он нужен, если размер виден в статусной строке.** Статусная строка
показывает долю окна в 1 млн токенов, и 300 тысяч выглядит как «занято всего
30 %». Занятость окна и цена запроса — разные величины: при 300 тысячах каждый
следующий запрос платит за 300 тысяч заново. Сторож называет вторую вслух.

Приём при срабатывании: дописать `docs/HANDOFF.md` → `/clear` → новая сессия
читает файл состояния и продолжает.

## Как перемерить

Транскрипты: `~/.claude/projects/-home-mvv-Projects-trihology/*.jsonl`.
В каждой строке ответа есть `message.usage` и `message.model`.

Вес запроса: `input + output×5 + cache_read×0,1 + cache_creation×1,25`.

```bash
python3 - <<'PY'
import json, glob, collections
ves_i=ves_o=ves_cr=ves_cc=0
po_sess=collections.Counter(); maks_ctx=collections.Counter()
id2tool={}; instr=collections.Counter()
for f in sorted(glob.glob('/home/mvv/.claude/projects/-home-mvv-Projects-trihology/*.jsonl')):
    sid=f.split('/')[-1][:8]
    for line in open(f, errors='ignore'):
        try: d=json.loads(line)
        except Exception: continue
        m=d.get('message') or {}
        u=m.get('usage')
        if u and (u.get('cache_read_input_tokens') or u.get('input_tokens')):
            ves_i+=u.get('input_tokens',0); ves_o+=u.get('output_tokens',0)
            ves_cr+=u.get('cache_read_input_tokens',0); ves_cc+=u.get('cache_creation_input_tokens',0)
            po_sess[sid]+=u.get('cache_read_input_tokens',0)
            ctx=(u.get('input_tokens',0)+u.get('cache_read_input_tokens',0)
                 +u.get('cache_creation_input_tokens',0))
            if ctx>maks_ctx[sid]: maks_ctx[sid]=ctx
        c=m.get('content')
        if isinstance(c,list):
            for b in c:
                if not isinstance(b,dict): continue
                if b.get('type')=='tool_use': id2tool[b.get('id')]=b.get('name','?')
                elif b.get('type')=='tool_result':
                    nm=id2tool.get(b.get('tool_use_id'),'?'); cc=b.get('content'); n=0
                    if isinstance(cc,str): n=len(cc)
                    elif isinstance(cc,list):
                        for x in cc:
                            if isinstance(x,dict):
                                n += len(x.get('text','')) if x.get('type')=='text' else (4000 if x.get('type')=='image' else 0)
                    instr[nm]+=n
ves=ves_i+ves_o*5+ves_cr*0.1+ves_cc*1.25
vs=sum(instr.values())
print(f"вес {ves:,.0f}; чтение кэша {100*ves_cr*0.1/max(ves,1):.0f}% веса")
print(f"три длиннейшие сессии: {100*sum(v for _,v in po_sess.most_common(3))/max(ves_cr,1):.0f}% чтения кэша")
for nm,v in instr.most_common(8): print(f"  {nm:<20} {100*v/max(vs,1):>5.1f}%")
potolok=sum(maks_ctx.values())
print(f"сходимость: выдача инструментов ~{vs//4:,} токенов <= сумма пиков контекста "
      f"{potolok:,} -> {'да' if vs//4<=potolok else 'НЕТ, где-то пересчёт'}")
PY
```

**Про последнюю строку.** Сравнивать выдачу инструментов с **накопленным** чтением
кэша бесполезно: чтение кэша суммируется по всем запросам и выходит на три порядка
больше, поэтому такая проверка проходит всегда и не ловит ничего. Сторож, который
не может сработать, — это ровно тот дефект, за который отсюда же выброшена проверка
на повторное чтение.

Знаменатель, при котором проверка кусается, — **пик контекста**: всё прочитанное
остаётся в контексте, значит выдача инструментов обязана помещаться в сумму пиков
по сессиям. Померено на `trade`: 792 731 токен выдачи против суммы пиков
6 165 785 — это 13 % потолка вместо прежних 0,026 %.

Запас всё ещё восьмикратный, и это честный предел приёма: считать пик **по каждой
сессии отдельно** было бы строже, но давало бы ложные тревоги там, где контекст
сжимался — после сжатия накопленная выдача законно превышает пик.

Чего проверка при таком запасе стоит: ошибку в разы она пропустит, а ошибку в
десятки и сотни раз — поймает. Ловушка с картинками (счёт по длине base64 вместо
площади) даёт как раз два порядка, то есть попадается. Прежняя проверка не поймала
бы и её: там нужно было бы ошибиться в четыре тысячи раз.

**Общее правило, чтобы не выбросить приём целиком.** Проверка вырождается не
всегда, а когда стороны **разной природы**: разовый объём против накопленной
суммы. Если обе стороны накопленные — она работает и кусается. У соседей именно
так был пойман ошибочный разностный счёт: 5 808 млн против 3 100 млн, расхождение
в 1,9 раза видно сразу, ещё до разбора причин. Поэтому сравнивать надо либо
накопленное с накопленным, либо разовый объём с суммой пиков контекста.

⚠️ И следить за единицами: слева токены, справа тоже токены. Сравнить символы
выдачи с токенами контекста — ошибка вчетверо, ровно в ту сторону, которая
успокаивает.

## Четыре ловушки замера

Проверены на своей шкуре при разборе `trade`; в трёх из четырёх легко
оказаться, не заметив.

1. **Имя инструмента в транскрипте — `Agent`, не `Task`.** Поиск по `Task`
   даёт ноль при сотнях запусков.
2. **Слэш-команду человека нельзя искать среди вызовов `Skill`.** Она приходит
   в его же реплике как `<command-name>orchestrate</command-name>`.
3. **Картинку нельзя мерить длиной base64.** Тарифицируется по площади,
   `ширина × высота / 750`. Ошибка на два порядка.
4. **Расход нельзя раскладывать разностью контекста соседних запросов.** При
   восстановлении сессии контекст сбрасывается и возвращается целиком, и
   разность читает абсолютный размер как прирост.

Дешёвая проверка, ловящая три из четырёх: **сумма долей обязана укладываться в
фактическое чтение кэша.** Она есть в скрипте выше последней строкой.

Пятая ловушка, найденная здесь: **выдача инструмента лежит в двух местах**.
`message.content` → `tool_result` — то, что увидела модель. Отдельное поле
`toolUseResult` — полная запись на диске, крупная выдача `Bash` в ней целая, а
модели ушла урезанная. Для расхода контекста считать надо первое.

## Чего в сторожах намеренно нет

**Проверки на повторное чтение файла.** Она была в первой редакции и снята по
замеру, а не по недосмотру: дословных повторов среди выдач оказалось 0,2 % у
`trade` и 0,23 % в третьем проекте, причём все повторы мельче порога — то есть
сторож не поймал бы ни одного и срабатывал бы только ложно. Все «повторные
открытия» были **разными кусками одного файла**, то есть новым содержимым.

Если захочется вернуть — сначала померить долю дублей по `md5` тела
`tool_result` у себя. У нас этого замера нет: мерить не на чем (замер 1).

**Понимания чужого рабочего каталога.** Размер файла проверяется через
`os.path.isfile` относительно каталога, в котором запущен хук, то есть корня
проекта. Поэтому `cd /другой/каталог && cat крупный_файл` проходит, если файла
с таким именем нет ещё и в корне проекта. Так в этой же сессии читались
транскрипты соседнего проекта. Развернуть `cd` сторож не может по той же
причине, по какой не разворачивает переменные: это было бы исполнением команды.
Известное ограничение, не дефект — но помнить о нём стоит: чтение по
абсолютному пути (`cat /home/mvv/...`) проверяется нормально, а после `cd` —
нет.
