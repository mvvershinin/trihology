# План: сборка под Windows

**Дата**: 2026-08-08
**Цель**: автономный дистрибутив под Windows — распаковал папку, запустил, работает.
Без установки Python, без установки зависимостей, без прав администратора.

---

## Про базу данных: устанавливать нечего

SQLite — не сервер и не отдельная программа. Это библиотека, вшитая внутрь
самого Python: модуль `sqlite3` входит в стандартную поставку, и файл движка
(`sqlite3.dll` + `_sqlite3.pyd`) лежит рядом с интерпретатором. PyInstaller
кладёт его в дистрибутив вместе со всем остальным.

Практически это значит: **ни установщика СУБД, ни службы, ни сетевого порта, ни
пароля, ни прав администратора**. Вся база — один файл `phototrichogram.db` в
папке пользователя. Скопировали файл — скопировали всю базу; это же делает
готовый пункт меню «Файл → Резервная копия».

Отдельная приятная мелочь: файл базы двоично совместим между Linux и Windows.
База, снятая на Linux, откроется на Windows и наоборот.

## Что уже готово и переносить не нужно

Проверено по коду, работы не требует:

- **Пути** — везде `pathlib.Path`, разделители подставляются сами.
- **Шрифты** — DejaVu лежит в `assets/fonts/` внутри пакета, кириллица в PDF не
  зависит от того, что установлено в системе.
- **Колесо мыши** — уже привязано и по-виндовому (`<MouseWheel>` + `event.delta`),
  и по-иксовому (`Button-4/5`). Обе ветки на месте, в обоих прокручиваемых
  виджетах.
- **Зависимости** — opencv-headless, numpy, Pillow, matplotlib, fpdf2. У всех
  готовые колёса под Windows, ничего не собирается из исходников.
- **tkinter** — входит в поставку Python с python.org, PyInstaller кладёт Tcl/Tk
  в дистрибутив.
- **build.spec** — писался с прицелом на Windows, нужные поля (`console`, `icon`)
  уже присутствуют, комментарии это оговаривают.
- **Драйвер микроскопа** — USB-микроскопы это UVC-устройства, у Windows драйвер
  встроенный. Скрипт `install-udev.sh` — чисто линуксовая вещь, на Windows
  аналога не нужно.

## Решение, без которого не начать: где собирать

**PyInstaller не умеет собирать под чужую систему.** Exe под Windows делается
только на Windows. Варианты:

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Живая Windows-машина** (рекомендую) | Сразу же и тестируется с реальным микроскопом | Нужна машина с USB-микроскопом |
| Виртуалка Windows на этом же Linux | Не нужно второе железо | Проброс USB-камеры в VM капризен; тест камеры недостоверен |
| GitHub Actions, windows-runner | Сборка сама по кнопке, воспроизводимо | Камеры в облаке нет — проверить микроскоп нельзя, только что exe запускается |

Что важно понять: **собрать exe и проверить, что он работает с микроскопом — две
разные задачи**. Первую можно отдать хоть облаку. Вторую — только живая Windows
с воткнутым микроскопом. Код камеры под Windows я написать могу, но проверить
его без такой машины нельзя, и я не буду делать вид, что проверил.

## Фаза 1. Камера под Windows  ⏱ 1 день · главная работа

Единственный по-настоящему платформозависимый кусок — `core/camera.py`.

### 1.1 Выбор backend

Сейчас: `cv2.CAP_V4L2` на Linux, `cv2.CAP_ANY` на остальных. `CAP_ANY` под
Windows выбирает MSMF, а он для дешёвых USB-микроскопов плох: открывается по
несколько секунд, часть моделей отдаёт чёрный кадр, настройки экспозиции часто
не применяются.

Делаем: на Windows пробовать `CAP_DSHOW` (DirectShow) первым, `CAP_MSMF` —
запасным. DirectShow с такими микроскопами работает надёжнее.

Выбор backend — в конфиг (`CameraConfig.backend`: `auto` | `dshow` | `msmf` |
`v4l2`), дефолт `auto` = разумный выбор по системе. Правило проекта: пороги и
режимы настраиваются, а не прибиваются гвоздями.

### 1.2 Имя камеры в списке

Сейчас `_device_name()` читает модель из `/sys/class/video4linux/...`, а если не
вышло — возвращает строку `/dev/video0`. На Windows не выйдет никогда, и
пользователь увидит в списке камер «/dev/video0», чего на Windows не существует.
Это прямая ложь в интерфейсе.

Два пути:

- **Просто**: на Windows показывать «Камера 0 (640×480)». Честно, без вранья, но
  две одинаковые камеры не различить, и запоминание выбора между запусками
  (сейчас оно опирается на имя модели) станет опираться только на индекс.
- **Правильно**: добавить `pygrabber` — маленький пакет, спрашивает у DirectShow
  настоящие имена устройств («USB 2.0 Camera»). Тогда логика запоминания камеры
  работает на Windows ровно как на Linux. Цена — одна зависимость, только для
  Windows.

Рекомендую второй: запоминание камеры уже написано и опирается на имя; ломать
его ради экономии одного пакета не стоит.

### 1.3 Перечисление устройств

`list_devices()` перебирает индексы 0..9 и пробует открыть каждый. На Windows
через MSMF это несколько секунд на несуществующий индекс — интерфейс встанет
колом на полминуты. С DirectShow быстрее; с `pygrabber` список берётся сразу и
перебор вообще не нужен.

### 1.4 Мёртвое поле в конфиге

`CameraConfig.video_format` («YUYV») объявлено, но нигде не используется — код
формат потока не задаёт. Либо выкинуть поле, либо задействовать (на Windows
осмысленно ставить MJPG: дешёвые микроскопы на YUYV режут частоту кадров).
Разбираться в этой же фазе, чтобы не тащить мусор в релиз.

**Файлы**: `core/camera.py`, `utils/config.py`, `gui/capture_tab.py` (список
камер), тесты камеры. **Слои** не нарушаются, камера и так в core.

## Фаза 2. Пути и логи  ⏱ 2 часа

### 2.1 Папка логов

`main.py` пишет лог в `~/.local/share/phototrichogram/` — это линуксовое
соглашение (XDG). На Windows получится нелепое `C:\Users\Имя\.local\share\...`.

Делаем: лог рядом с настройками и базой, в `~/.phototrichogram/`. Одна папка на
всё — и пользователю понятнее, и резервная копия проще.

### 2.2 Лог при окне без консоли

В оконной сборке Windows у процесса нет консоли, и `sys.stdout` равен `None`.
Сейчас обработчик лога создаётся как `StreamHandler(sys.stdout)` безусловно —
на Windows он молча перестанет работать. Файловый лог уцелеет, но обработчик
надо ставить по условию, а не наугад.

### 2.3 Подсказки про apt

`_REQUIRED_PACKAGES` при нехватке пакета советует `sudo apt install python3-tk`.
В собранном дистрибутиве это не всплывёт (там всё на месте), но советовать
пользователю Windows команды Debian всё равно нельзя. Подсказки — по системе.

**Файлы**: `main.py`, `utils/config.py`.

## Фаза 3. build.spec под Windows  ⏱ 3 часа

- **`console=True` → на Windows `False`.** Иначе за окном программы будет висеть
  чёрное окно консоли. На Linux параметр ни на что не влияет, так что делаем
  ветку по системе внутри spec.
- **Иконка.** Сейчас `assets/icon.png`. Windows требует `.ico` (многоразмерный:
  16/32/48/256). Кладём `assets/icon.ico` рядом и выбираем по системе.
- Остальное в spec трогать не нужно: `hiddenimports`, `datas` со шрифтами,
  отключённый UPX — всё это одинаково верно для обеих систем. UPX не включать
  тем более: сжатые им exe чаще ловят ложные срабатывания антивирусов.
- **Сборка**: `pyinstaller build.spec` на Windows даёт папку
  `dist\phototrichogram\` с `phototrichogram.exe` внутри.

**Файлы**: `build.spec`, `assets/icon.ico` (новый).

## Фаза 4. Проверка на живой машине  ⏱ 0.5 дня · нужна Windows с микроскопом

Проверять по порядку:

1. Программа запускается из распакованной папки, чёрной консоли нет.
2. Микроскоп виден в списке, имя нормальное, а не «/dev/video0».
3. Живое видео идёт, кадры сохраняются.
4. Калибровка проходит.
5. Анализ снимка даёт те же числа, что на Linux (взять один и тот же файл
   снимка — числа обязаны совпасть, вычисления от системы не зависят).
6. База создаётся, пациент заводится, история строится.
7. PDF-отчёт формируется, кириллица на месте.
8. Резервная копия и восстановление базы работают.
9. Проверить на машине, где Python не установлен вообще — это и есть смысл
   слова «автономно».

## Фаза 5. Раздача дистрибутива  ⏱ 2 часа

**Формат: ZIP с папкой.** Распаковал куда угодно, запустил exe. Ровно то, что
просили: без установки. Размер — на Linux дистрибутив занимает 281 МБ, на
Windows выйдет похоже, в ZIP сожмётся примерно вдвое.

Про «один файл вместо папки» (onefile): не советую. Такой exe при каждом запуске
распаковывает себя во временную папку — старт вместо секунды занимает 10–20, и
антивирусы реагируют на это заметно нервнее.

**Про предупреждение Windows.** Неподписанный exe при первом запуске покажет
синее окно SmartScreen «Windows защитила ваш компьютер». Это не ошибка сборки и
не лечится кодом — только покупкой сертификата подписи (порядка 200–400 $ в год).
Пока сертификата нет, в инструкции описываем: «Подробнее» → «Выполнить в любом
случае». Сказать об этом пользователям заранее — иначе решат, что это вирус.

Установщик (Inno Setup, ярлык в меню «Пуск») — потом, если захочется. На
автономность он не влияет.

## Риски, названные честно

1. **Микроскоп может не завестись с первого раза.** Дешёвые USB-микроскопы
   ведут себя по-разному с DirectShow и MSMF. Поэтому выбор backend вынесен в
   настройки: если не пошло — переключается, а не переписывается.
2. **Проверить камеру без железа нельзя.** Тестами покрывается логика выбора
   backend и разбор списка устройств, но не то, что конкретный микроскоп отдаёт
   картинку. Это честное ограничение, а не недоработка тестов.
3. **SmartScreen напугает пользователей.** Лечится только подписью; до тех пор —
   абзац в инструкции.
4. **Одинаковые числа на Linux и Windows.** Сегментация и измерения от системы не
   зависят, но версии OpenCV/NumPy обязаны совпадать. Пины в `requirements.txt`
   уже это обеспечивают; в фазе 4 сверяем на одном и том же снимке.
